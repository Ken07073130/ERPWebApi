# 单项目分层说明

> 技术栈：ASP.NET Core 8 Web API · EF Core 8（SqlServer）· JWT
> 前端：Vue 3 + Element Plus（独立仓库，HTTP + CORS 交互）
> 适用范围：内部 ERP / MES 生产管理系统

---

## 一、先说清楚：为什么不是 `src/` 多项目

`docs/后端架构与目录结构.md` 里画的是**多项目版本**（`src/ERP.Domain` 等 4 个 csproj）。那是目标形态，**磁盘上从未创建过**。

当前采用**单项目 + 文件夹分层**，理由：

| 维度 | 单项目分层（当前） | 多项目拆分 |
|---|---|---|
| 立刻开写 | 可以，不打断节奏 | 要先搬 Program.cs、改命名空间 |
| 依赖约束 | **靠纪律，编译器不拦** | 编译期强制，引错就报错 |
| 改动成本 | 移动文件即可 | 改 csproj、改引用、改 using |
| 适用时机 | 1~2 人、单一服务 | 多模块、多人协作 |

**核心代价要认下来**：下面第三节的依赖规则在单项目里**只是约定**。任何人一个 `using ERPWebApi.Infrastructure;` 就能穿透，编译器不会拦。所以这份规则需要自觉遵守。

## 二、目录结构

```
ERPWebApi/                            ← 单项目根，表现层入口也在这里
│
├── Controllers/                      # ④ 表现层 —— HTTP 入口
│   └── WeatherForecastController.cs  #    模板遗留，待删
│
├── Application/                      # ② 应用层 —— 用例编排
│   ├── Abstractions/                 #    接口契约（仓储、服务）
│   ├── Common/                       #    Result、分页、错误码
│   └── Features/                     #    按业务功能垂直切分
│       └── Auth/
│           └── Dtos/                 #    登录请求/响应模型
│
├── Domain/                           # ① 领域层 —— 业务规则核心
│   ├── Common/                      #    实体基类、领域异常
│   ├── Entities/
│   │   └── Identity/                #    User、Role 等身份实体
│   └── Enums/                       #    领域枚举
│
├── Infrastructure/                   # ③ 基础设施层 —— 实现细节
│   ├── Persistence/
│   │   └── Configurations/          #    EF Core 实体映射
│   ├── Identity/                    #    密码哈希、JWT 签发
│   └── Repositories/                #    仓储实现
│
├── Properties/
├── appsettings.json
├── appsettings.Development.json
├── Program.cs                       #    组合根：DI 注册都在这
└── ERPWebApi.csproj
```

> 每个目录里的 `.gitkeep` 是空目录占位（git 不跟踪空目录）。目录一有真实文件就可以删掉它。

### 各层职责

| 目录 | 职责 | 绝对不要出现 |
|---|---|---|
| `Domain/` | 业务规则、实体行为、领域异常 | EF Core、ASP.NET Core、JSON、任何 NuGet |
| `Application/` | 用例编排：取数据 → 调实体 → 保存 | `DbContext`、`SqlClient`、`HttpContext` |
| `Infrastructure/` | 数据库、外部系统、密钥签发 | 业务规则（不许写 `if (订单金额 > 1000)`） |
| `Controllers/` | 收请求、调 Application、返回 HTTP 状态码 | 业务规则、`DbContext`、`Infrastructure` 命名空间 |

## 三、依赖规则（唯一正确的方向）

```
Controllers  ──→  Application  ──→  Domain
     │                                 ↑
     └──→  Infrastructure  ───────────┘
```

四个模块与 `ERPWebApi` 命名空间的对应关系：

- `ERPWebApi.Domain`
- `ERPWebApi.Application`
- `ERPWebApi.Infrastructure`
- `ERPWebApi.Controllers`

**允许的引用方向：**

1. `Domain` → 谁都不引
2. `Application` → 可引 `Domain`
3. `Infrastructure` → 可引 `Application`、`Domain`（**反向引用，这是依赖倒置的落点**）
4. `Controllers` → 可引 `Application`；**不要**引 `Infrastructure`

**唯一的例外**：`Program.cs` 需要 `using ERPWebApi.Infrastructure;` 来调用 DI 注册扩展方法。除此之外，`Controllers/` 里不应出现 Infrastructure 的类型。

### 自查方法

写完一个文件，问自己一句：**「这东西换掉数据库/换掉认证方式，需要改吗？」**

需要改的，说明它不属于 Domain 或 Application。

## 四、登录功能具体往哪放

按这个清单落位，一步都不会错：

| 要写的东西 | 放哪 |
|---|---|
| `User` 实体 | `Domain/Entities/Identity/User.cs` |
| 实体基类（Id / 创建时间 / 创建人） | `Domain/Common/BaseEntity.cs` |
| 业务异常（区别于系统异常） | `Domain/Common/DomainException.cs` |
| `IUserRepository` 接口 | `Application/Abstractions/IUserRepository.cs` |
| `IJwtTokenService` 接口 | `Application/Abstractions/IJwtTokenService.cs` |
| `LoginRequest` / `LoginResponse` | `Application/Features/Auth/Dtos/` |
| 登录编排逻辑（查用户 → 验密码 → 签发） | `Application/Features/Auth/AuthService.cs` |
| `AppDbContext` | `Infrastructure/Persistence/AppDbContext.cs` |
| User 表映射（唯一索引、字段长度） | `Infrastructure/Persistence/Configurations/UserConfiguration.cs` |
| `UserRepository` 实现 | `Infrastructure/Repositories/UserRepository.cs` |
| `JwtTokenService` 实现 | `Infrastructure/Identity/JwtTokenService.cs` |
| `AuthController` | `Controllers/AuthController.cs` |
| DI 注册 | `Program.cs` |

**判断原则**：接口在 `Application/Abstractions`，实现在 `Infrastructure/`。`AuthService` 只依赖接口，不 `new` 任何具体类。

### 两条落位时最容易搞错的

1. **`User` 实体的行为写在实体里。** 比如「密码错误时递增失败次数、超阈值则锁定」，应该写成 `User` 上的方法，而不是在 `AuthService` 里写一堆 `user.FailedCount++`。这正是四层和三层最大的差别——**实体是充血的，不是数据袋子。**

2. **`LoginResponse` 里不能有 `PasswordHash`。** 响应模型要在 `Dtos/` 里白名单式地定义字段，别图省事直接返回 `User` 实体。

## 五、什么时候该升级为多项目

出现下面任一条，就该把 `Domain` 先抽成独立项目（它零依赖，最好抽）：

- 开始写**第二个业务模块**（生产 / 库存 / 质检），且模块间耦合度低
- 有**第二个人**加入，需要靠编译器而不是靠口头约束守分层
- 发现已经有人无意间**穿透了分层**（例如 `Controllers` 里出现了 `DbContext`）

升级可以分步做，不必一次到位：`Domain` → `Application` → `Infrastructure`。每抽一层，编译一次，确保没破坏。
